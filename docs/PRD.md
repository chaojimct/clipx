# clipx 产品需求文档（PRD）

> 状态：v1.0 · 2026-09-02 · 配套文档：[ARCHITECTURE.md](ARCHITECTURE.md)（技术方案）、[ROADMAP.md](ROADMAP.md)（里程碑与验收）

## 1. 背景

四个前置项目为这次规划提供了全部输入：

- **ClipboardX（WPF，v1.9.8）**：功能完整的 Windows 单平台版本，已长期日用。作为本产品的行为规格书。.NET 运行时基线内存约 96MB，无法满足内存目标。
- **clipboard-tauri / clipboard-tauri-clean**：两次 Tauri v2 原型，各约 1.7K 行，验证了交互设计（拼音搜索、快捷短语、键盘导航），但都停在"内存态历史 + 500ms 轮询"的原型阶段，未解决持久化与事件监听。
- **clipboardx-rs**：为 Rust 重写预留的空目录，即本仓库。

2026-09 的技术调研结论（详见 ARCHITECTURE.md §2）："全平台 + 10-30MB 内存"的组合没有现成方案——Tauri 系产品（PasteBar、EcoPaste 等）开发效率高但 WebView 内存超标；低内存标杆（Ditto 10-20MB、Maccy）全部是单平台原生实现。结论：用 Rust 原生渲染自建，这是唯一同时满足全平台与内存目标的路径。

## 2. 产品定位

clipx 是一个常驻系统托盘的跨平台剪贴板管理器：持续记录剪贴板历史，热键呼出不抢焦点的弹窗，搜索后一键粘贴回任意应用。

- 首要用户是开发者本人（dogfood 驱动开发），达标后开源发布。
- 差异化组合：原生渲染的内存占用（目标 10-30MB，对标 Ditto 的 10-20MB）+ Windows/macOS/Linux 全平台 + 内建 OCR + 拼音搜索。目前没有同时做到这四点的产品。

## 3. 核心场景

**场景 1：热键粘贴（最高频，定义产品成败）**
用户在任何应用里按 Ctrl+`（可配置），屏幕光标处弹出历史面板（不夺取当前输入焦点），键入关键词过滤（中文全拼、拼音首字母、英文），↑↓ 选择，Enter 粘贴回原应用，Esc 关闭。全程手不离键盘，两次按键完成一次"找回历史内容"。

**场景 2：找图片**
截图或复制的图片进入历史，列表显示缩略图；用户以图中文字搜索（OCR 建立索引），选中后原样粘贴回。

**场景 3：从 WPF 版迁移**
现有 ClipboardX 用户的全部历史（含图片与 OCR 结果）一次性导入，不丢数据。

**场景 4：后台常驻**
托盘图标常驻，内存占用不随历史增长显著膨胀；复制行为本身零感知（无弹窗、无卡顿）。

## 4. 功能清单

优先级定义：P0 = M0/M1 交付，产品成立的底线；P1 = M2/M3 交付，对齐 WPF 版体验；P2 = M4+ 交付或视需求排期。

### 4.1 采集与存储

| 功能 | 优先级 | 说明 | WPF 版基线 |
|---|---|---|---|
| 文本监听 | P0 | Windows 事件驱动（无轮询）；macOS changeCount 轮询（系统无事件 API） | 事件驱动 |
| 图片监听 | P0 | 位图采集，含尺寸元数据 | 有 |
| 文件列表监听 | P1 | 文件路径数组 | 有 |
| 富文本（HTML/RTF） | P1 | 存原始格式，粘贴时优先还原富文本 | 无（有意增强） |
| 内容去重 | P0 | 相同内容置顶而非新增；图片用 blake3 强哈希 | 有 |
| SQLite 持久化 | P0 | WAL 模式，重启不丢 | 有 |
| 历史容量 | P1 | 默认 2000 条可配置，超出淘汰最旧（pinned 豁免） | 有 |
| 来源应用记录 | P2 | 记录复制来源进程，用于展示与筛选 | 无 |

### 4.2 弹窗与交互

行为对齐 WPF 版，不重新设计。

| 功能 | 优先级 | 说明 |
|---|---|---|
| 热键呼出 | P0 | 默认 Ctrl+`，设置中可改 |
| 不抢焦点弹窗 | P0 | Windows WS_EX_NOACTIVATE 等价能力；Esc/失焦关闭 |
| 键盘导航 | P0 | ↑↓/Home/End 移动，Enter 粘贴，Ctrl+1~9 快选 |
| 列表虚拟化 | P0 | 2000 条滚动 60fps，只实例化可见行 |
| 类型筛选 | P1 | 在 全部/文本/图片/文件 间切换 |
| 右键菜单 | P1 | 粘贴、收藏、删除、复制内容 |
| 多屏定位 | P1 | 弹窗出现在鼠标所在屏（拒绝无效矩形，回退鼠标位置——WPF 版既定规则） |
| 收藏/固定 | P1 | pinned 条目不被容量淘汰，置顶展示 |
| 快捷短语 | P2 | 常用文本固定区（tauri 版验证过的交互） |

### 4.3 搜索

| 功能 | 优先级 | 说明 |
|---|---|---|
| 文本搜索 | P0 | 子串匹配，SQLite FTS5 |
| 拼音搜索 | P0 | 全拼 + 首字母（"文本" 匹配 wenben / wb），tauri 版验证过的需求 |
| OCR 文本搜索 | P1 | 图片经 OCR 后文字可搜 |
| 全文深搜 | P1 | 默认搜预览，需要时深搜全文/OCR |

### 4.4 粘贴回写

| 功能 | 优先级 | 说明 |
|---|---|---|
| 文本/图片/文件粘贴 | P0 | 写剪贴板 + 模拟 Ctrl/Cmd+V（WPF 版行为） |

### 4.5 图片与 OCR

| 功能 | 优先级 | 说明 |

## 5. 非功能需求

| 指标 | 目标 | 依据 |
|---|---|---|
| 常驻内存（托盘态） | ≤30MB，目标区间 10-30MB | 自实测 Rust+Slint 私有内存 7MB；Ditto 官方标称 10-20MB；M2 实测启动 23.1MB |
| 弹窗打开时内存 | 增量 ≤30MB，关闭后回落 | 大图预览不驻留；M2 实测 100 图连发峰值 82.8MB，空闲 trim 后回落 0.2MB |
| 热键 → 弹窗显示 | <150ms | WPF 版体感基线 |
| 捕获延迟 | Windows 即时（事件）；macOS ≤500ms（changeCount 轮询）；Linux X11 事件级 | macOS 无事件 API，Maccy 默认同为 500ms |
| 历史规模 | 默认 2000 条；万条不崩 | Slint ListView 虚拟化 |
| 冷启动 | ≤1s 到托盘就绪 | |
| 后台 CPU | 无操作时约 0% | 事件驱动，无忙轮询（macOS 轮询除外） |
| 平台 | Windows 10+（主力）/ macOS 12+ / Linux（X11 先行，Wayland 在 M7） | |
| 数据位置 | 便携模式（exe 同级 Data/）与安装模式（平台标准目录）双支持 | 沿用 WPF 版约定 |

内存说明：WPF 版经验表明历史条数不是内存主因（2000 条降到 800 条仅省约 0.4MB），图片 blob 与 OCR 中间数据才是。因此懒加载与释放纪律是硬约束，见 ARCHITECTURE.md §7。

## 6. 不做什么（v1 范围外）

| 排除项 | 理由 |
|---|---|
| 云同步（WebDAV/MQTT） | 单机价值先行；tiez-clipboard 已验证该方向，列为 v2 候选 |
| 插件/脚本系统 | CopyQ 式插件是其复杂度与内存问题的主要来源之一，v1 明确不要 |
| 移动端 / Web | 与定位不符 |
| 剪贴板加密/密码管理 | 与密码管理器职责重叠 |
| AI 功能 | v2 再议 |
| FileJump 文件夹跳转 / Everything 快速查找 | Windows-only 高级能力，与剪贴板核心正交；v1 不含，M4-M5 移植吸收（处置见 §7） |

## 7. Windows 高级功能（FileJump 与 Everything）

WPF Full 版的两大招牌功能在 clipx 中不进 v1，但不是永久排除。它们与剪贴板核心正交，且本质上是 Windows 专属能力：#32770 文件对话框注入、Total Commander / XYplorer / Directory Opus / WPS 的路径采集、Everything 本身，在其他平台都没有对应物。因此这不构成跨平台移植问题，只有"何时移植到 Rust"的问题，答案见 ROADMAP M4-M5（2026-09-02 排位评审：两项功能均高频日用、Mac 非日常机、无发布硬节点，已定先于 macOS 执行）。

过渡共存：WPF 版的 FileJumpOnly flavor（ClipboardX-filejump.exe，无剪贴板监听）与 clipx 并行运行，职责不重叠，热键不冲突；该 flavor 同时包含 Everything 快速查找（两者同属 CLIPX_FILEJUMP 门控，已从 WPF 源码核实），过渡期功能零缺失。代价是 Windows 上双进程双托盘，10-30MB 的整机内存目标要到 M5 完成才真正达成。

移植分两层：

- **Everything IPC（阶段一，对应 M4，约 1 周）**：WPF 版经 Everything64.dll SDK 调用；Rust 优先直连 Everything 的窗口消息 IPC（WM_COPYDATA），省去 DLL 分发与 FFI，FFI 绑定为备选。macOS/Linux 的近似能力（Spotlight、locate）不承诺。
- **FileJump（阶段二，对应 M5，主体）**：注入 DLL 与宿主语言无关，直接复用现有 native/ShellNavigate 产物；宿主侧移植三块——对话框检测（v1.9.7 的标题/子控件特征与 WPS 误判排除规则）、多文件管理器路径采集（Explorer COM / TC / XYplorer / DOpus）、注入调度与渐进退避重试（0/120/300/600/1000/1500ms）。

## 8. 与 WPF 版的对齐原则

WPF 版是行为规格书：弹窗交互、键盘行为、搜索语义、多屏定位规则逐项对齐，不重新发明。有意偏离的三处：

1. 富文本格式支持（WPF 版没有，属明确增强）
2. 拼音搜索从前端库移到核心层实现（行为不变，实现位置变化）
3. 内存目标从"尽力而为"变为硬性验收指标
